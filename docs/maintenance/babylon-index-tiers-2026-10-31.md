# Babylon reversible index-tier adapter · 2026-10-31

Increment B is **opt-in infrastructure only**. The normal Babylon entry does not import or instantiate it, fetch PLD2, or select reduced tiers. Full-detail default, existing distance/quality policy, original assets, sole custom physics solver, readiness/compilation deadlines and required native Mesa gate are unchanged. This is not a proposed Mesa driver workaround.

## Contract and pinned implementation

- `src/engine/babylon/existing-player-lods.ts` consumes the frozen actual-import binding table and trusted data returned by the shared hash-verifying `loadPlayerLods`. Its synchronous constructor does not independently rehash arbitrary caller-created objects: callers must preserve verified provenance and exclusive ownership of original arrays/resources. It defensively validates all row correspondences/ranges/aliases/source vertex IDs/error and triangle budgets, then privately snapshots derivative arrays and level selections before any mutation.
- Original index arrays are retained by identity; attributes, vertex buffers, geometry, the single global submesh, original bounds, materials, hierarchy, bones and animation owners are retained. It does not compact/reorder vertex attributes, clone models, change material/shader paths or independently dispose scene resources.
- Babylon **9.33.1** `Meshes/geometry.js:438–507`: `updateIndices` copies CPU indices and can recreate submeshes. `setIndexBuffer` clears CPU indices, forces submesh recreation and does not release the previous buffer. Therefore neither is used. Public `setIndices(target, originalVertexCount, false, true)` preserves the target CPU array and existing submesh after its full-stream index count is updated. The normal API invalidates VAOs and allocates replacement index buffers; it does not alter vertex buffers or bounds.
- `setIndices` releases the previous GPU buffer **before** allocating the replacement. No transactional rollback after allocation/driver failure is promised. No private geometry/GPU handles are introduced to simulate atomic publication.

## GPU ownership and failure

The supplied `BabylonPresentationGpu` must own the same scene/context; that association is a caller contract, not independently verified at runtime. Every index write, including restoration, runs through its existing `prepare` lane: drain the prior draw, acquire exclusive ownership, preflight the whole table again, commit synchronously, then observe the upload fence. This is not a visible-presentation receipt; a caller still needs completed ready rendered frames.

Cancellation before commit leaves every index/submesh unchanged and drains the empty lease without poisoning the owner. Cancellation after commit starts cannot abandon the upload: the pending call retains ownership until its fence completes. Live `dispose` cancels an uncommitted request or waits for a committed one, then restores the exact original arrays under a second lease. A safe preflight/deadline rejection permits an explicit disposal retry; it never extends the supplied deadline.

A commit/fence failure poisons the adapter; an owned-work failure also poisons the GPU owner. Rejection by an already-busy/unavailable owner does not claim to poison somebody else's existing lease. No partly modified model may resume. Uniform tier/triangle diagnostics become `null`, the first error remains authoritative, and later writes reject. The external owner performs normal container/scene teardown; only afterward may adapter disposal abandon its metadata without claiming restoration.

## Evidence and remaining acceptance

`tests/babylon-existing-player-lods.test.ts` imports the unchanged hash-verified original GLB through the normal loader using NullEngine, with all 172 primitives / 101 materials / 82 texture objects and 59 Babylon bones (58 authored palette joints). It loads the actual hash-verified PLD2, exercises every tier and exact full restoration, retained source/attribute arrays and resource identities, all-row prevalidation, private derivative snapshots, both cancellation boundaries, restoration/disposal, busy ownership, failure at the fourth allocation, first-error precedence, no future use and context loss. Combined with the existing binding suite: **21/21 passed locally**. NullEngine establishes data/lifecycle contracts, not GPU allocation, texture pixels, performance or visual parity.

`e2e/fixtures/babylon-player-lods.ts` and `e2e/babylon-player-lods.spec.ts` add an isolated **real-WebGL probe, not yet executed locally**. It uses the original asset/materials/textures, 1440×900 fixed camera, existing neutral steering, all 172 normal shader preparation jobs and the unchanged 120000ms total budget. Tiers `0 → 1 → 2 → 3 → 0` each require two completed ready GPU frames. The probe compares actual GPU-buffer index values with the verified original/PLD2 streams, checks unchanged resources/pose and released replaced buffers, captures every tier and demands exact final full-detail pixel restoration. Baseline pose is recorded only after the first completed full-detail presentation, including normal linked-bone synchronization. Reduced-tier images are evidence to inspect, **not** a claim of pixel equality with full detail. GPU handles/readback exist only inside this isolated test fixture.

Required Actions execution, screenshot inspection, the original native full-detail Mesa gate, production distance/quality-policy integration and representative hardware/gameplay acceptance remain separate, unsatisfied gates. No automatic tier policy or performance claim is enabled by these tests.
