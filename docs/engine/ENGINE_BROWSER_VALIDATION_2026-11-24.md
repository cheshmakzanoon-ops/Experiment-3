`idbKv`, and `FrameBufferPool` modules. Every test gets a fresh Playwright browser
context and a routed localhost document. Native IndexedDB requests, transactions,
structured cloning, version-change events, and a dedicated browser Worker are
used. No existing browser profile, personal saved game, resource asset, or
authored scene is opened or changed.

| Case | Intended native behavior checked | Local execution |

The Worker case checks the shared pool through a small dedicated Worker; it is
not a claim that the complete physics-worker/browser route has executed. The
storage cases exercise real browser storage when run, but do not exercise the
Electron filesystem bridge or its cross-process behavior.

## Focused CI path

The existing `ci.yml` manual trigger has no file-selection input and runs the
complete browser inventory across 16 shards. Its ordinary coverage remains
unchanged. The new `engine-runtime-validation.yml` adds a bounded, read-only
diagnostic job for exactly the six native cases and the complete replay-state
scenario.

It uses Ubuntu 24.04 and Node 22, records the source commit/tree and dependency
lock digest, installs locked dependencies, and runs the TypeScript compiler and
Vite directly under the existing source-stability guard. It does not invoke
asset-generation build hooks. The browser command uses the existing configuration,
verified Mesa llvmpipe backend, Xvfb, one worker, zero retries, original assertions
and original test deadlines. Reports, backend identity, build identity and source
receipts upload on either success or failure. The job has only `contents: read`,
does not retain checkout credentials, and cannot deploy or commit updates.

Run the focused browser selection on an environment supporting the existing
browser backend with:

```sh
APEX_BROWSER_BACKEND=mesa LIBGL_ALWAYS_SOFTWARE=true GALLIUM_DRIVER=llvmpipe \
xvfb-run -a -s '-screen 0 1920x1080x24' \
node node_modules/@playwright/test/cli.js test \
e2e/engine-native-lifecycle.spec.ts e2e/replay-state.spec.ts \
--workers=1 --retries=0 --forbid-only
```

The workflow triggers on relevant source/test changes on `main` and also supports
manual dispatch. A queued workflow is not a pass. Native browser execution,
software rendering, physical GPU performance and physical audio/controller
acceptance are separate claims; this assignment establishes none of the latter.
